# Story 12.2 — Alteração de Senha de Aluno pelo Admin

## Status

Draft

## Story

**Como** administrador da plataforma Mentoria IA,
**Quero** poder redefinir a senha de um aluno diretamente na página de gestão de alunos,
**Para** resolver rapidamente situações em que o aluno perdeu o acesso sem depender do fluxo de e-mail.

## Critérios de Aceite

- [ ] AC-1: Cada linha da tabela "Matriculados" em `AdminAlunosPage` exibe um botão `🔑` na coluna de ações, ao lado dos botões existentes (✏️, ⏸/▶/↩, ✕, 🗑)
- [ ] AC-2: Clicar em `🔑` abre modal com título "Redefinir senha — {nome completo do aluno}"
- [ ] AC-3: O modal contém dois campos: "Nova senha" e "Confirmar nova senha" (ambos `type="password"`) + botão "Redefinir" + botão "Cancelar"
- [ ] AC-4: Se as senhas não coincidem, erro inline "As senhas não coincidem" é exibido e o formulário não é submetido
- [ ] AC-5: Se a senha tem menos de 8 caracteres, erro inline "Senha deve ter pelo menos 8 caracteres" é exibido e o formulário não é submetido
- [ ] AC-6: Ao submeter dados válidos, uma requisição `POST /api/admin/students/{id}/password` com `{ password }` é enviada com o Bearer token do admin
- [ ] AC-7: O endpoint backend valida autorização (`verifyAdmin`), valida comprimento mínimo (≥8), e chama `supabase.auth.admin.updateUserById(id, { password })`
- [ ] AC-8: Em caso de sucesso, o modal fecha e a lista recarrega (sem mensagem de sucesso especial — comportamento padrão da página)
- [ ] AC-9: Em caso de erro do backend, a mensagem de erro é exibida dentro do modal (sem fechá-lo)
- [ ] AC-10: O botão "Redefinir" fica desabilitado durante o loading para evitar double-submit
- [ ] AC-11: Requisições sem token admin válido recebem resposta 403 "Acesso negado"
- [ ] AC-12: O visual do modal, campos e botões segue exatamente o padrão já existente em `AdminAlunosPage` (`inputStyle`, `labelStyle`, componente `Modal` local, CSS vars)

## Dev Notes

### Padrão de endpoint a replicar
O novo arquivo `api/admin/students/[id]/password.js` deve espelhar a estrutura de `api/admin/students/[id].js`:

```js
// api/admin/students/[id]/password.js
import { createClient } from '@supabase/supabase-js';

function makeClient() {
  return createClient(
    process.env.VITE_SUPABASE_URL,
    process.env.SUPABASE_SERVICE_KEY
  );
}

async function verifyAdmin(req, supabase) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return false;
  const { data: { user } } = await supabase.auth.getUser(token);
  return user?.user_metadata?.role === 'admin';
}

export default async function handler(req, res) {
  const supabase = makeClient();
  if (!(await verifyAdmin(req, supabase))) {
    return res.status(403).json({ error: 'Acesso negado' });
  }

  const { id } = req.query;

  if (req.method === 'POST') {
    const { password } = req.body;
    if (!password || password.length < 8) {
      return res.status(400).json({ error: 'Senha deve ter pelo menos 8 caracteres' });
    }
    const { error } = await supabase.auth.admin.updateUserById(id, { password });
    if (error) return res.status(500).json({ error: 'Erro ao redefinir senha' });
    return res.json({ ok: true });
  }

  return res.status(405).json({ error: 'Method not allowed' });
}
```

### Routing — verificar suporte à rota aninhada
A rota `api/admin/students/[id]/password.js` cria um nível adicional de aninhamento. Verificar que o servidor (Vite dev + Vercel) suporta este padrão. O projeto já usa `api/materials/[id]/download.js` — mesmo padrão, logo deve funcionar.

[Nota: Fallback reference — padrão já utilizado em `api/materials/[id]/download.js`]

### Supabase Admin — updateUserById
`supabase.auth.admin.updateUserById(userId, { password })` requer a `SUPABASE_SERVICE_KEY` (chave de serviço, não a anon key). Esta operação invalida sessões ativas do usuário por padrão no Supabase Auth.
