## 1. Overview

Adicionar à página `AdminAlunosPage` a capacidade de um admin redefinir a senha de qualquer aluno diretamente, sem enviar e-mail de recuperação. A ação é iniciada via botão dedicado na linha do aluno, abre um modal exclusivo e chama a API Supabase Admin (`updateUserById`) no backend, que já possui `SUPABASE_SERVICE_KEY`.

### 1.1 Goals

- FR-1: Admin pode redefinir a senha de qualquer aluno matriculado a partir da página de gestão
- FR-2: Operação é realizada sem envio de e-mail e sem interação do aluno
- FR-3: Nova senha passa por validação mínima de segurança (mínimo 8 caracteres) antes de ser enviada
- FR-4: Admin recebe feedback visual claro sobre sucesso ou falha da operação

### 1.2 Non-Goals

- Auto-envio de notificação por e-mail ao aluno (fora de escopo — decisão do admin)
- Histórico de redefinições de senha
- Expiração forçada de sessões ativas do aluno após redefinição
- Redefinição em lote (múltiplos alunos de uma vez)
- Redefinição de senha para usuários na aba "Aguardando cadastro"

## 2. Requirements Summary

### 2.1 Functional Requirements

| ID   | Descrição | Prioridade | Fonte |
|------|-----------|------------|-------|
| FR-1 | Exibir botão "🔑" (chave) na coluna de ações de cada aluno matriculado, ao lado dos botões existentes | P0 | Solicitação do usuário |
| FR-2 | Clicar no botão "🔑" abre modal dedicado "Redefinir senha" com o nome do aluno no título | P0 | Solicitação do usuário |
| FR-3 | Modal contém: campo "Nova senha" + campo "Confirmar senha" + botão "Redefinir" + botão "Cancelar" | P0 | Solicitação do usuário |
| FR-4 | Validação inline: senhas não coincidem → erro exibido antes do submit | P0 | Consistência com `ResetPasswordPage` (12.1) |
| FR-5 | Validação inline: senha com menos de 8 caracteres → erro inline | P0 | NFR de segurança |
| FR-6 | Submit chama `PATCH /api/admin/students/:id/password` com `{ password }` | P0 | Decisão técnica |
| FR-7 | Backend chama `supabase.auth.admin.updateUserById(id, { password })` com service key | P0 | Decisão técnica — service key já disponível |
| FR-8 | Sucesso: fechar modal + exibir feedback positivo inline na tabela ou via `actionError` limpo | P0 | Consistência UX com outras ações |
| FR-9 | Erro do backend: exibir mensagem de erro no modal sem fechá-lo | P1 | Consistência com modais existentes |

### 2.2 Non-Functional Requirements

| ID    | Categoria | Requisito | Métrica |
|-------|-----------|-----------|---------|
| NFR-1 | Segurança | Senha nunca trafega em log — apenas via HTTPS no body da requisição | Zero logs de senha |
| NFR-2 | Segurança | Mínimo 8 caracteres exigido (acima do mínimo Supabase de 6) | Validação client + server |
| NFR-3 | Usabilidade | Botão "Redefinir" desabilitado durante loading (evita double-submit) | Estado `saving` igual ao padrão da página |
| NFR-4 | Consistência visual | Modal segue exatamente o padrão do componente `Modal` já existente em `AdminAlunosPage` | Reutilização do componente `Modal` local |
| NFR-5 | Consistência visual | Inputs seguem `inputStyle` e `labelStyle` já definidos na página | Zero CSS extra |
| NFR-6 | Autorização | Endpoint protegido pela mesma função `verifyAdmin` dos outros endpoints de aluno | Consistência — nenhum endpoint de admin sem autenticação |

### 2.3 Constraints

| ID    | Tipo | Constraint | Impacto |
|-------|------|------------|---------|
| CON-1 | Tecnológico | Supabase Admin API: `supabase.auth.admin.updateUserById(userId, { password })` requer `SUPABASE_SERVICE_KEY` — já disponível no backend (`api/admin/students/[id].js`) | Nenhum setup adicional |
| CON-2 | Tecnológico | Supabase exige senha com mínimo de 6 caracteres; a plataforma eleva para 8 (NFR-2) | Validação dupla: client (≥8) e server (≥8, antes de chamar Supabase) |
| CON-3 | Visual | Manter padrão de `inline styles` com CSS vars — não introduzir CSS modules ou Tailwind | Consistência com `AdminAlunosPage` existente |
| CON-4 | Arquitetura | A lógica de redefinição admin NÃO deve passar pelo `AuthContext` — é uma operação de admin sobre outro usuário, não sobre a própria sessão | Separação de responsabilidades |
| CON-5 | Rota | Criar rota dedicada `api/admin/students/[id]/password.js` para separar semanticamente de `PATCH [id]` (que atualiza perfil) | Clareza de API e facilidade de auditoria |

## 3. Technical Approach

### 3.1 Architecture Overview

Fluxo direto sem envolvimento do `AuthContext` (CON-4):

```
[AdminAlunosPage]
  Botão 🔑 → setModal({ type: 'change-password', student })
       │
  Modal "Redefinir senha"
  input nova senha + confirmar senha
  validação inline client-side
       │
  POST /api/admin/students/:id/password
  { password }  (Bearer token admin)
       │
  [api/admin/students/[id]/password.js]
  verifyAdmin() → supabase.auth.admin.updateUserById(id, { password })
       │
  { ok: true } ──► fechar modal
  { error }   ──► exibir erro no modal
```

### 3.2 Component Design

**Modificações em `AdminAlunosPage.jsx`:**

1. Adicionar botão `🔑` na coluna de ações (antes do botão `🗑`), visível para todos os alunos matriculados
2. Adicionar `type: 'change-password'` ao sistema de modais existente (`modal` state)
3. Adicionar função `handleChangePassword({ password })` — análoga às funções `handleEdit` e `handleDelete`
4. Adicionar modal `{modal?.type === 'change-password'}` com formulário dedicado
5. Adicionar componente local `ChangePasswordForm` (ou inline no modal) com dois campos de senha e validação

**Novo arquivo de API:**

- `api/admin/students/[id]/password.js` — endpoint `POST` exclusivo para redefinição de senha

### 3.3 Data Flow

```
Frontend:
  handleChangePassword({ password })
    → headers = await authHeaders()
    → POST /api/admin/students/{user_id}/password
      body: { password }
    → success: setModal(null) + load()
    → error: setActionError(data.error)

Backend (password.js):
  verifyAdmin(req, supabase)
  validar password.length >= 8
  supabase.auth.admin.updateUserById(id, { password })
  → { ok: true } ou { error }
```

### 3.4 `ChangePasswordForm` — Estrutura

```jsx
// Estado: newPassword, confirmPassword, localError
// Validações:
//   - newPassword.length < 8 → "Senha deve ter pelo menos 8 caracteres"
//   - newPassword !== confirmPassword → "As senhas não coincidem"
// Submit: onSave({ password: newPassword })
// Campos:
//   - "Nova senha" (type="password", required)
//   - "Confirmar nova senha" (type="password", required)
// Botões:
//   - "Redefinir" (submit, disabled quando loading, estilo var(--accent))
//   - "Cancelar" (type="button", onCancel)
```

## 6. Testing Strategy

### 6.1 Unit Tests — Backend

| Teste | Cobre | Prioridade |
|-------|-------|------------|
| `POST` com token admin válido e senha válida → chama `updateUserById` e retorna `{ ok: true }` | FR-7 | P0 |
| `POST` sem token → retorna 403 | NFR-6 | P0 |
| `POST` com token de não-admin → retorna 403 | NFR-6 | P0 |
| `POST` com `password` ausente → retorna 400 | CON-2 | P0 |
| `POST` com `password` com menos de 8 caracteres → retorna 400 | CON-2, NFR-2 | P0 |
| `POST` com erro do Supabase → retorna 500 com mensagem | FR-9 | P1 |

### 6.2 Unit Tests — Frontend

### 6.3 Acceptance Tests (Given-When-Then)

```gherkin
Feature: Alteração de senha de aluno pelo admin

  Scenario: Admin redefine senha com sucesso (FR-1 a FR-8)
    Given o admin está na página Gestão > Alunos, aba Matriculados
    When clica no botão 🔑 de um aluno
    Then o modal "Redefinir senha — {nome do aluno}" é exibido
    When preenche "Nova senha" com "NovaSenha123" e "Confirmar nova senha" com "NovaSenha123"
    And clica em "Redefinir"
    Then o modal fecha
    And o aluno consegue fazer login com a nova senha

  Scenario: Senhas não coincidem (FR-4)
    Given o modal de redefinição está aberto
    When preenche "Nova senha" com "Senha123" e "Confirmar" com "Senha456"
    Then vê erro inline "As senhas não coincidem"
    And o formulário não é submetido

  Scenario: Senha muito curta (FR-5, NFR-2)
    Given o modal de redefinição está aberto
    When preenche "Nova senha" com "abc" e "Confirmar" com "abc"
    Then vê erro inline "Senha deve ter pelo menos 8 caracteres"
    And o formulário não é submetido

  Scenario: Erro de rede ou Supabase (FR-9)
    Given o modal está aberto e o backend retorna erro
    When admin submete senhas válidas
    Then vê mensagem de erro no modal
    And o modal permanece aberto para nova tentativa

  Scenario: Acesso não autorizado (NFR-6)
    Given uma requisição direta a POST /api/admin/students/:id/password sem token admin
    Then recebe 403 "Acesso negado"
```

## 7. Risks & Mitigations

| Risco | Probabilidade | Impacto | Mitigação |
|-------|--------------|---------|-----------|
| Admin redefine senha do aluno acidentalmente (UX) | Média | Médio — aluno perde acesso | Modal com nome do aluno no título reforça contexto; botão 🔑 visualmente distinto |
| Sessões ativas do aluno não são invalidadas após reset | Alta | Baixo a curto prazo | Documentado como Non-Goal; Supabase invalida sessões antigas ao mudar senha via `updateUserById` por padrão |
| Rota `/[id]/password.js` conflita com rota existente `/[id].js` | Baixa | Médio | Testar routing no ambiente de dev antes de mergear |
| `SUPABASE_SERVICE_KEY` ausente em ambiente de dev local | Baixa | Médio | Documentar no `.env.example`; endpoint retorna 500 claro se key ausente |
